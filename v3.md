# Changes for v3

This file collects changes that would break users or Go importers and so wait for the next major version. It is a list of
candidates, not a promise: nothing here is decided until it has an issue and a maintainer's yes. Add an entry when a change is
held back because it breaks something, and remove it when it ships or is dropped. Do not put these changes into a v2 release.

## Go library

### Move the Go files out of the repository root

The root of the repository is one Go package, `package jactionlint`, with 540 files (277 of them tests, about 150,000 lines).
The command, the playground, the fuzz targets and some scripts import it. Only `cmd/jactionlint`, `internal/exampleconfig` and
`internal/runscript` live in their own directories.

For v3, split the root package into packages in subdirectories and leave no `.go` file in the root, so the root holds the module
files, the docs, the data and the configuration.

This breaks every importer of `github.com/jdx/jactionlint/v2`, so it needs a new module path, `github.com/jdx/jactionlint/v3`.
The root package has about 1,570 exported functions and 324 exported types, counted with `grep` on the `func` and `type`
declarations at the start of a line (methods are not in the function count).

Questions to settle before the work starts:

- Which of the exported names are API that v3 promises, and which only became exported because the root was one package? Everything
  else goes under `internal/`.
- Is there a small public package (for example `github.com/jdx/jactionlint/v3/lint` with `Linter`, `Options`, `Rule`, `Error`
  and the formatters), with the rest internal?
- Keep a thin facade in the root for the callers of the v2 names, or none? "No Go file in the root" rules out the facade, so the
  answer is no unless that goal changes.
- The package split follows the dependency order, so the work needs a map of which files depend on which. Start from the leaves:
  the YAML and expression parsers, the AST, the context and type model, the generated data (`popular_actions.go`,
  `all_webhooks.go`, `availability.go`), then the rules, then the linter and the command line.
- Paths in the tests (`testdata/`), in the generators (`scripts/generate-*`, `go generate` lines), in `docs/rules.md`,
  `CONTRIBUTING.md`, `.github/workflows/` and the goldens must follow the move. `TestSchemasAreUpToDate` and the rules
  documentation check run from the root today.
- The release flow must not break: `release-please-config.json` and the `extra-files` list, `action.yml`, `.pre-commit-hooks.yaml`,
  the wasm build for the playground and the Homebrew cask.
- Do the move in a quiet period (no open pull requests that touch Go files) and in steps, with `git mv` so the history follows.
  Every open pull request conflicts with a move.

### State the library's versioning

[docs/api.md](docs/api.md) and `doc.go` say that the version belongs to the command and that the library may break in a patch
release. With a defined public package, v3 can promise semantic versioning for that package only, and say that `internal/`
has no promise.

## Command line and config

### Remove what v2 only deprecates

- The config keys that `--migrate-config` rewrites: `timeout-minutes`, `require-commit-hash`, `require-permissions`,
  `require-checkout-before-local-action`, `require-expression-wrapping`, `check-falsy-ternary`, `check-workflow-run-names`,
  `require-shell` and `max-run-lines`. v2 reads them with a warning. v3 would make them an error that names the replacement.
- The profile names `strict` and `all`, which are read as `pedantic` with a warning.
- The retired rule IDs that the config and ignore comments still accept (`renamedRules` in `rule_registry.go`). v3 would stop
  accepting them. Keep `--migrate-config` working for a v2 file as the way out.

### Move rules into the default profile

A rule that is pedantic in v2 only because its false-positive rate was not measured on a large corpus can move to `default` in
v3, where a new finding is no longer a surprise because the release says so. The profile `default` becomes stricter, which is why
it waits for a major version; the [v2 migration guide](docs/v2-migration.md) already warns that a clean repository may fail.

Candidates are decided one rule at a time from measured numbers, not by a list written here. Do not move a rule whose findings
depend on a heuristic of the shell (`unredacted-secrets` in run scripts, `macos-gnu-flags`, the TOCTOU rules) without a
measurement on real repositories.

### Dates GitHub has set

- `pull_request_target` is off by default from 2026-11-02. The message and docs of `dangerous-triggers` can say so in v2, but
  whether the rule's default severity or profile changes with it is a v3 question.
- Runner labels and Node versions that GitHub retired: v3 can stop warning about labels that are long gone and drop the
  corresponding data.
